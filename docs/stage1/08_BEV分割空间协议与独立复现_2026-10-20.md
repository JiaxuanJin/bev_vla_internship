# BEVFormer 分割低 IoU 根因排查进展（截至 2026-10-20）

## 1. 问题与目标

在 DriveLM799 子集和 nuScenes Val 上发现地图分割前景 IoU 明显低于作者公开报告，需要确认评估协议一致性、训练/推理空间约定，并在独立场景和完整 Val 中验证最小修复。此处记录已完成的验证、能够排除的假设和仍需核实的差异，不把候选提升写为正式修复。

## 3. 已核实的事实

- Step 38 核实官方 Val PKL 为 6019 帧、150 个场景、token 无重复；作者前景 mIoU 公式按三类全局 IoU 平均，混淆矩阵重算与已有指标一致。
- 使用 checkpoint：`/mnt/g/nus/bevformer_small_seg.pth`，SHA256 `b9e369ba2e4514050fefe914f57565a31b918edaa735958a1f877184ad75dc68`，元数据 `epoch=4`、`iter=112520`，包含分割 decoder 权重。
- Step 46 的六相机投影和 LiDAR 投影可视化检查没有发现显著整体失效，但不能代替全网络投影正确性验证。
- Step 50 在独立作者环境中通过作者 `single_gpu_test` 完成 81 帧，独立环境为适配 RTX 5080 使用了新版 PyTorch/CUDA 和少量运行时兼容补丁；**不属于作者当时完全一致的依赖栈**。
- Step 51 静态一致不等于训练时执行代码一致；Step 53 合成坐标误差为零也不等于真实预测正确；Step 54 的实际指标下降是反对直接合并当前平移修正的证据。

## 4. 当前仍存在的疑问

1. **作者高分实验的历史产物身份**：取得约 40% Mini Val 指标时所用 checkpoint SHA256、训练 git commit、依赖栈、完整 Config 和测试命令，是否就是现在这组？
2. **GT 生成与地图数据版本**：官方 Mini 的 PKL、地图层、RasterizeMapVectors、ego2global 位置/方向以及样本顺序，是否与作者历史运行完全一致？
3. **训练时空间语义**：checkpoint 的 Config 已核对，但训练时真实源码没有审计到。BEV 特征的轴向与 GT Ego 网格如何对应，是否在训练阶段被学习为固定约定？
4. **方向候选的退化**：Transpose 在部分场景大幅提升、部分场景退化，属于数据/协议差异，还是方向映射不具普适性？
5. **修复验收**：目前没有在 Mini 两场景和正式 Val 6019 帧上同时验证三类 IoU 稳健提升的修复方案。

## 5. 下一步（按优先级）

**P0：锁定高分复现条件。** 向作者/维护者核对训练源码版本、checkpoint、Mini PKL/nuScenes 地图版本和完整运行命令；特别留意公开权重和当时实验记录是否真正对应。

**P0：逐帧对齐 GT/预测物理位置。** 固定若干 Mini 和正式 Val 样本，保存同一帧的摄像头输入、BEV feature、Slicer 取样位置、预测 mask 和 GT，并检查真实物理世界点在各阶段是否对应。先只读诊断，不再通过搜索各种 flip/rot90 拟合 GT。

**P1：若定位到明确差异，再做最小修复和独立验证。** 冻结其余因素，分别报告 Divider、Ped Crossing、Boundary IoU，Mini 两场景交叉验证后复跑官方 Val 6019 帧；记录 checkpoint 与结果哈希。
