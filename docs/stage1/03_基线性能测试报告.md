# 第一阶段：BEVFormer-Small 基线性能测试报告

**实验日期**：2026-10-10—2026-10-12  
**任务**：基于已有预训练 BEVFormer-Small 在 nuScenes Mini 和 DriveLM–nuScenes v1.1 的 799 帧子集上进行 3D 检测与 BEV 地图分割评估，并输出图像示例。  
**报告性质**：本地独立帧基线实验记录，**不是完整官方 nuScenes Val 的基线排行榜结果**。

## 1. 实验环境

| 项目 | 版本/配置 |
|---|---|
| GPU | NVIDIA GeForce RTX 5080 Laptop GPU，16 GB 显存 |
| 开发系统 | WSL Ubuntu 22.04 / VS Code |
| Python | 3.10（当前 `.venv-bevformer` 环境） |
| PyTorch | 2.8.0+cu128（截图中已验证 CUDA 可用） |
| MMDetection3D / MMCV | 使用本地已跑通的兼容环境；精确包版本建议从 `pip freeze` 另存，不在此猜测 |
| 检测模型 | BEVFormer-Small，已有 `bevformer_small_epoch_24.pth` |
| 地图分割模型 | BEVFormer-Small-Seg，已有 `bevformer_small_seg.pth` |

**不涉及新模型训练/微调**：本阶段加载已有权重，模型进入 `eval` 模式，在 `torch.no_grad()` 下执行前向传播和指标计算。

## 2. 数据与评估协议（最重要）

### 2.1 nuScenes Mini

- 训练索引 323 帧、8 场景；验证索引 81 帧、2 场景。
- 用于测试开发环境、官方预训练模型加载与最小评估链路。
- 这里的数据样本规模与场景难度**不同于完整 nuScenes Val**。

### 2.2 DriveLM 799 帧子集

- 来自 DriveLM v1.1 验证 QA 所关联的 **799 个 nuScenes 官方 val sample token**；跨 149 个驾驶场景。
- 使用原 nuScenes Trainval 元数据和官方 GT，验证了 799/799 的 token 归属、图像、六路标定、车辆位姿。
- 因为 DriveLM 关键帧不是连续视频流，此次使用**独立帧协议**：检测时使用独立帧信息 PKL，分割时保留官方 `scene_token` 并显式关闭 `video_test_mode`；避免稀疏帧间错误复用历史 BEV。
- 检测的 mAP/NDS：对 799 个 token 截取官方 3D GT，并借用 nuScenes Devkit 的标准检测匹配、类别距离阈值与指标计算；**评估样本数是自定义子集**，不是完整 Val 官方评估。
- 分割的 mIoU：基于真实地图标签与四类 BEV 栅格预测，按全体像素累计混淆矩阵（行 GT、列预测）计算 IoU。

**特别强调**：检测 mAP/NDS、分割 mIoU 都是自动驾驶视觉/地图感知指标，**不是 DriveLM 语言问答正确率**。

## 3. 执行流程与可复现命令

下列命令均需在 `~/projects/bev_vla` 根目录、已激活 `.venv-bevformer` 的 WSL 终端执行；数据、权重需按本机路径布置。

```bash
# ① DriveLM 官方 QA 数据转换：单场景验证、全量转换
python scripts/run_drivelm_official_preprocess.py --mode smoke
python scripts/run_drivelm_official_preprocess.py --mode full

# ② DriveLM 799 帧推理前数据验证（已通过 0、399、798 三帧）
python scripts/test_drivelm_799_bevformer_loader.py --indices 0,399,798

# ③ 3D 检测：799 帧 GPU 推理、随后与 GT 子集评估
python scripts/run_drivelm_799_det_all.py --limit 799
python scripts/evaluate_drivelm_799_det_subset.py

# ④ BEV 分割：3 帧冒烟测试后自动跑完 799 帧并输出 mIoU
python scripts/run_drivelm_799_seg_all.py --limit 799
```

检测、分割脚本包含进度恢复，但不要在不知道缓存来源时混用另一套 PKL 或权重。执行前可核对脚本中的 config/PKL/checkpoint 路径；并非所有系统都适合直接复制到新机器运行。

### 4.2 DriveLM 799 帧 BEV 分割评估细节

模型输出四通道 logits，解析为四类像素标签，GT 与预测均为 **200×400**。

| 类别 | 799 帧累计像素 IoU |
|---|---:|
| 0：背景 `background` | 0.735245（73.52%） |
| 1：分隔线 `divider` | 0.020841（2.08%） |
| 2：人行横道 `ped_crossing` | 0.080718（8.07%） |
| 3：边界 `boundary` | 0.052075（5.21%） |
| **前景 mIoU（不含背景，1–3）** | **0.051211（5.12%）** |
| **四类 mIoU（含背景，0–3）** | **0.222220（22.22%）** |
| 799 帧 GPU + 地图 GT 计算耗时 | 519.77 秒 |

计算方式：

$$
\mathrm{IoU}_c = \frac{TP_c}{TP_c + FP_c + FN_c}, \qquad
\mathrm{mIoU}_{fg} = \frac{\mathrm{IoU}_1 + \mathrm{IoU}_2 + \mathrm{IoU}_3}{3}.
$$

本地是**先把 799 帧的混淆矩阵相加，后计算各类别 IoU**，而非对各帧 mIoU 直接做算术平均。

主要文件：

- `outputs/drivelm_check/seg799_independent_eval/metrics_summary.json`
- `outputs/drivelm_check/seg799_independent_eval/per_frame.csv`
- `outputs/drivelm_check/seg799_independent_eval/confusion.npy`
- `outputs/drivelm_check/seg799_independent_eval/progress.json`

## 6. 已排查问题与尚未解决的限制

**已验证**：

1. 检测权重、分割权重已被严格加载，模型可以真实进行 GPU 前向推理。
2. DriveLM 799 帧六路图像与 nuScenes token 对齐，标定存在，数据加载正常。
3. 分割类别为 `0: background, 1: divider, 2: ped_crossing, 3: boundary`；`argmax` 通道解码符合 `CrossEntropyLoss(use_sigmoid=False)` 的输出设计。
4. 分割 IoU 采用全局混淆矩阵累计；基本统计公式正确。
5. 检查了 CAN Bus、位姿和 BEV slicer 的局部几何一致性，尚无充分证据能证明某一种错误是唯一根因。

**尚未解决**：

- 分割低前景 mIoU（Mini 6.38%；799 帧 5.12%）及视觉错位。可能与推理数据预处理、坐标协议、任务权重、栅格/地图映射、历史 BEV 配置等因素有关，目前**不作确定性归因**。
- **未在完整 nuScenes 官方 Val 的标准连续时序条件下对齐作者论文指标**；自定义 DriveLM 子集不应进入官方排行榜成绩对照表。
- `test_llama.json` 记录数 29,450 与官方 README 参考 29,448 尚有 2 条差异，需要后续逐条核查，不影响已经完成官方函数运行和结构检查这一事实。

### 改进建议（第二阶段/后续复核，不属于“本次已完成”）

先对照开源分割仓库原始评估入口、元数据的空间范围及预训练时序协议，并对同帧的相机、地图和 BEV 坐标做一致性检验；如需改动，则在固定一组验证样本上做**预先规定的**对照试验，记录每次变更与结果，避免事后调图凑分。

## 7. 综合结论

第一阶段技术目标中的环境、DriveLM 官方 QA 预处理、预训练基线运行、真实 799 帧感知推理、mAP/NDS 与 mIoU 计算及可视化已形成可核验记录。最重要的局限是本实验属于**稀疏独立帧基线**且分割质量较弱。后续工作的重点不是宣称当前数值“复现了完整官方 SOTA”，而是提高跨数据集/时序协议下的严格可比性并验证分割空间对齐。
